# Olist E-Commerce: SQL Feature Engineering

## Про проєкт

Цей проєкт виконаний у межах домашнього завдання з SQL та Data Engineering.

Основна мета — навчитися працювати з реальними даними інтернет-магазину, підготувати їх для подальшого використання в Machine Learning та дослідити продуктивність SQL-запитів.

Для роботи використано **Olist Brazilian E-Commerce Dataset**, який містить інформацію про клієнтів, замовлення, товари та продавців.

## 🛠 Використані технології

- **PostgreSQL** — робота з базою даних та SQL-запитами.
- **Python** — завантаження та обробка даних.
- **Pandas** — робота з таблицями.
- **SQLAlchemy** — підключення до PostgreSQL.
- **Google Colab** — середовище виконання.
- **KaggleHub** — завантаження датасету.

## 📊 Основні етапи роботи

### 1. Підготовка даних

Завантажено п'ять таблиць датасету Olist:

- `olist_customers`
- `olist_orders`
- `olist_order_items`
- `olist_products`
- `olist_sellers`

Створено окремі RAW-таблиці та typed-схему з відповідними типами даних, первинними й зовнішніми ключами.

### 2. Feature Engineering через CTE

Побудовано SQL-pipeline із використанням Common Table Expressions (CTE).

Розраховано основні ознаки клієнтів:

| Feature | Опис |
|---|---|
| `recency_days` | Кількість днів від останнього замовлення |
| `frequency` | Кількість замовлень клієнта |
| `monetary` | Загальна сума покупок |
| `cohort_quarter` | Квартал першої покупки |
| `avg_order_value_30d_recent` | Середня вартість замовлень за останнє 30-денне вікно |
| `cancellation_rate` | Частка скасованих замовлень |
| `preferred_category` | Категорія товарів із найбільшими витратами |

Для розрахунків використано `JOIN`, `GROUP BY`, агрегатні та віконні функції.

### 3. Recursive CTE

Створено тестову таблицю `hw5_referrals` для моделювання зв'язків між клієнтами.

За допомогою `WITH RECURSIVE` реалізовано обхід графа та визначення глибини referral-зв'язків.

Для захисту від нескінченної рекурсії використано масив `path_ids` і обмеження `depth < 50`.

### 4. Materialized View

Створено `mv_olist_customer_features` для збереження готових ML-ознак.

Додано `UNIQUE INDEX` на `customer_id` та реалізовано оновлення через `REFRESH MATERIALIZED VIEW CONCURRENTLY`.

Це дозволяє повторно використовувати підготовлені дані без необхідності щоразу виконувати весь SQL-pipeline.

### 5. Аналіз продуктивності

За допомогою `EXPLAIN (ANALYZE, BUFFERS)` досліджено виконання SQL-запитів.

| Запит | Час виконання |
|---|---:|
| Розрахунок RFM через CTE | 623,644 мс |
| Пошук клієнта через MV | 0,130 мс |
| Вибірка Top-10 через MV | 39,515 мс |

У процесі аналізу розглянуто операції `Hash Join`, `GroupAggregate`, `HashAggregate`, `Seq Scan`, `Index Scan` та `Sort`.

*Примітка: запити виконують різний обсяг роботи, тому наведені результати не є прямим порівнянням швидкості однакових операцій.*
